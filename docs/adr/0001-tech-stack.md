# ADR-0001 技术栈选型

- 状态：已采纳
- 日期：2026-11-13
- 决策人：罗東明（A）、（B 填入）

---

## 背景

从零搭建一个「校园场地与自习室时段预约」系统，两人协同开发，主要目的是系统性覆盖 Java Web 的知识点，而不是尽快上线。因此选型的第一优先级是 **"能不能让我们踩到该踩的坑"**，第二优先级才是开发效率。

## 决策

| 层 | 选型 | 版本 |
|---|---|---|
| 语言 | Java | JDK 21 (LTS) |
| 框架 | Spring Boot | 3.x 最新稳定版（以 start.spring.io 实际生成的为准） |
| 持久层 | MyBatis-Plus + 手写 XML | 3.5.x |
| 数据库 | MySQL | 8.0 |
| 认证 | JWT + 自定义拦截器 | jjwt 0.12.x |
| 接口文档 | SpringDoc OpenAPI (Swagger UI) | 2.x |
| 单元测试 | JUnit 5 + Mockito | 随 Spring Boot |
| 集成测试 | Testcontainers（阶段 3 引入） | — |
| 缓存 | Redis 7（阶段 2 引入） | — |
| 构建 | Maven | 3.9.x |
| 容器 | Docker（阶段 3 引入） | — |

**前端策略：阶段 1–2 不写前端页面。** 用 Swagger UI 和 Apifox 调用接口验证，把全部精力放在后端。前端是另一个独立的技能树，同时开工会让两个人一起掉进坑里。

## 备选方案与放弃理由

| 备选 | 为什么放弃 |
|---|---|
| Spring Data JPA | 自动生成 SQL 会隐藏索引和执行细节。阶段 2 要练「慢查询 → 看执行计划 → 加索引」，必须能看见并控制 SQL |
| MyBatis-Plus 全量使用 | 它的 Wrapper 写复杂查询会让人失去写 SQL 的能力。约定：单表基础 CRUD 用 Plus，**涉及多表、聚合、分页优化的查询一律手写 XML** |
| Spring Security | 功能完整但抽象层太厚，很难看清"一个请求到底怎么被拦下的"。阶段 1 用几十行的自定义拦截器，能把链路看得一清二楚；阶段 3 再评估是否替换 |
| 一开始就上 Spring Cloud 微服务 | 两人项目没有真实的服务边界压力，上微服务等于把分布式复杂度全吃下来、收益为零。改为"模块化单体"，最后只做一次真实拆分 |
| Vue / React 前端 | 不属于本项目要覆盖的知识面，且会消耗掉一半以上的时间 |

## 后果

**变好的地方**

- 能看见并掌控 SQL，索引调优、执行计划、事务边界都是真实可练的
- 拦截器手写一遍，请求链路上每个环节都清楚了
- 没有前端负担，两个人可以把时间全押在后端深度上

**要付的代价**

- MyBatis 的 XML 比 JPA 啰嗦，前期会写不少样板配置
- 自定义拦截器不如 Spring Security 完备，后续要补权限模型（RBAC）时得自己设计
- 没有前端页面，答辩时展示效果偏弱（可接受，用 Swagger 演示）

## 什么时候该重新审视这份 ADR

- 阶段 3 发现自定义拦截器撑不住 RBAC 的复杂度
- 阶段 4 做服务拆分时发现模块边界划错了
